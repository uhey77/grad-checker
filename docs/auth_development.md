# 認証の開発手順

## 登録とログイン

`task setup` / `make setup` で依存を同期し、`task dev` / `make dev` で起動する。`auth-dev` も同じ構成を起動する。
画面は `http://127.0.0.1:5173`、Go APIは `127.0.0.1:8000`、Python内部サービスは `127.0.0.1:8001`。

1. 新規登録でユーザー名とパスワードを入力する。ユーザー名は半角英数字・アンダースコアの3〜32文字で、大文字小文字を区別せず小文字で保存する。
2. 一度だけ表示される復旧コードを安全な場所に保管し、保管確認後にログインへ進む。
3. ユーザー名とパスワードでログインする。別のブラウザー・端末でも同じアカウントを利用できる。
4. ログアウトと、再読込み時のセッション維持を確認する。

メールアドレス・大学ドメイン制限・メール認証・SMTP設定は使用しない。大学の公式アカウントとは別のアプリ専用アカウント。アカウントはSQLiteに保存する。通常の開発起動では開発DBを使うが、自動テスト・実装の検証は一時DBで行う。
ログイン後は所属設定を表示し、CS学部4課程のカリキュラムから本人の所属を保存・復元できる。選択肢には `task backend-seed` / `make backend-seed` で投入したマスタを使用する。適用年度未確認はそのまま表示する。成績・履修予定・判定履歴の本人用保存は今後の対象。

## パスワードの復旧

ログイン画面の「パスワードを忘れた場合」から、ユーザー名・復旧コード・新しいパスワードを入力する。
成功するとパスワードを更新し、すべての既存セッションを失効させ、新しい復旧コードを一度だけ表示する。旧コードは再使用できない。
新しいコードを保管してからログインする。パスワードと復旧コードを両方失った場合の復旧は提供しない。
コードの原値は画面のメモリだけに保持し、ブラウザーストレージには保存しない。画面を閉じたり再読み込みしたりすると再表示できない。
DBにはランダム32バイトから生成した復旧コードのSHA-256ハッシュのみを保存し、コードの照合・更新とセッション失効を同一トランザクションで行う。

## 設定と保護

| 設定 | 用途・既定 |
|---|---|
| `DATABASE_URL` | SQLite接続先。既定はbackend/data/grad_checker.db |
| `PUBLIC_ORIGIN` | 画面のオリジン。既定http://127.0.0.1:5173。公開時はHTTPS |
| `AUTH_SESSION_HOURS` | セッションの有効期限。既定24時間 |
| `AUTH_PASSWORD_MIN_LENGTH` / `AUTH_PASSWORD_MAX_LENGTH` | 既定12／128文字 |
| `AUTH_ATTEMPT_WINDOW_MINUTES` / `AUTH_ATTEMPT_LIMIT` | 登録・ログイン・復旧それぞれで接続元別と正規化ユーザー名別の試行上限。既定15分で5回。成功も数える |

画面のパスワード長は `/api/auth/config` から取得する。パスワードはArgon2id（19 MiB、反復2、並列度1）で保存する。
Goを単独起動する場合の `-public-origin` はPythonの `PUBLIC_ORIGIN` と一致させる。
CookieはHttpOnly／SameSite=LaxでHTTPSではSecureも付与する。更新系はOriginを検証し、ログアウト・所属保存はセッションに紐づくCSRFトークンも要求する。
公開プロキシ配下で信頼する接続元の認定、公開先、バックアップ・保持期間は配備時に決める。メール費用は不要だが、公開基盤の無料枠適合は別途確認する。

## 旧メール認証DB

起動時に空の旧studentsテーブルはemail_verified_at列をcreated_atへ改名し、認証情報に復旧コードのハッシュ列を追加する。
既存の科目データは変更せず、旧email_verificationsテーブルも自動削除しない。新規DBにはこの旧テーブルを作成しない。
旧メール認証アカウントが存在するDBでは起動を停止する。アカウントの削除・メールからのユーザー名の推測・パスワードの書換えは行わない。
その場合はDBのバックアップを取り、既存利用者のユーザー名と復旧コード発行の移行方針を決めてから移行する。
